Remote findings

CRITICAL PHP2SHELL-CVE-2026-109618
CVE-2026-109618: Upload-progress unserializer use-after-free / remote memory disclosure
PHP parses RFC1867 multipart requests during request startup, before normal module initialisation. Session upload-progress handling can publish a session id in PS(id); an out-of-memory error aborts the request before cleanup, leaving that pointer dangling. A later multipart request handled by the same worker can URL-encode the reclaimed heap into a PHPSESSID response cookie, disclosing live worker memory (passwords, tokens, API keys, certificates). The decoder side (BG(unserialize) bookkeeping published across a fatal allocation failure) is the memory-corruption primitive that chains with the disclosure into unauthenticated RCE.

Impact: Unauthenticated remote code execution as the web worker account (validated over HTTP against mod_php with default php.ini input and memory limits, and against prefork configurations with multiple workers). Also unauthenticated, application-agnostic process-memory disclosure - works even when the application never calls session_start().
Detected PHP 8.1.2 via X-Powered-By / Server header; fixed in PHP 8.5.12, 8.4.27, 8.3.36, 8.2.35.
Remediation. Upgrade to PHP 8.5.12, 8.4.27, 8.3.36, 8.2.35 (or your vendor's backport). If you cannot patch today, set session.upload_progress.enabled = Off and isolate the host behind the vendor WAF rules for this disclosure.

CRITICAL PHP2SHELL-CVE-2026-109619
CVE-2026-109619: Fatal-error backtrace use-after-free / OPcache type confusion
PHP retains the backtrace of the most recent fatal error in EG(last_fatal_error_backtrace). A fatal out-of-memory error destroys the request heap without undefining that executor-global value, so the worker keeps a pointer into the previous request's memory. If the same worker emits a diagnostic early in the next request it follows attacker-reclaimed memory. A second variant is an OPcache type confusion: an allocation failure during zend_accel_script_persist() advances the process-local CG(map_ptr_last) frontier without publishing the shared frontier, so another worker can reuse a slot for a different runtime object and shared metadata resolves to a pointer of the wrong type.

Impact: Unauthenticated heap use-after-free, memory disclosure and remote code execution with web worker privileges. Demonstrated pre-auth RCE against Drupal (backtrace UAF) and WordPress (OPcache type confusion).
Detected PHP 8.1.2 via X-Powered-By / Server header; fixed in PHP 8.5.12, 8.4.27, 8.3.36, 8.2.35.
Remediation. Upgrade to PHP 8.5.12, 8.4.27, 8.3.36, 8.2.35 (or your vendor's backport). If you cannot patch today, set session.upload_progress.enabled = Off and isolate the host behind the vendor WAF rules for this disclosure.

MEDIUM PHP2SHELL-MITIGATE
Interim mitigation available while you schedule the upgrade
- Disable session upload progress: session.upload_progress.enabled = Off (php.ini or per-pool php_admin_value). This removes the known abuse case and is the primary stop-gap for end-of-life branches.
- Remove the exposure instead of hiding it: upgrade to PHP 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35, or apply the vendor backport for your distribution.
- Count multipart request starts per worker and cap the number of simultaneous unfinished uploads (php_fpm process limits, request_terminate_timeout).
- Keep memory_limit realistic; the bug is triggered on allocation failure, so an absurdly low limit widens the trigger surface and an unlimited one removes the OOM path entirely, which is why 0/unlimited is not a recommended 'fix'.
- Put the PHP runtime behind a WAF/CDN rule set that the vendor published for this disclosure (Cloudflare, Fastly, AWS, Google Cloud, Imperva, Akamai).
- Isolate end-of-life PHP from the internet; never expose php-cgi (CVE-2024-4577 style argument injection also applies).
- Rotate any secret that lived in an affected worker's memory: DB passwords, APP_KEY / salts, API keys, TLS private keys, SMTP credentials.
PHP security advisory 2026-10-21.
Remediation. Apply the php.ini / pool changes, then restart the SAPI.

INFO PHP2SHELL-DETECT-GUIDANCE
Post-compromise and exploitation indicators to hunt for
- Unusual multipart/form-data requests followed by memory-limit errors or repeated HTTP 500 responses from the same worker.
- Unexpectedly large or malformed PHPSESSID response cookies (percent-encoded binary blobs from worker memory).
- Unexplained PHP worker churn: workers exiting or respawning in bursts without matching request volume.
- PHP worker (php-fpm, php-cgi, httpd, apache2) spawning sh, bash, cmd.exe, powershell.exe, python, perl, curl, wget, nc or certutil.
- Command lines containing /dev/tcp/, mkfifo, or PHP one-liners writing a temp .php file, executing it and deleting it.
- Recon burst straight from the web server: whoami, id, uname -a, ipconfig.
Wiz detection guidance + Huntress process-lineage hunting advice.
Remediation. Feed these into your SIEM/EDR. If any of them fired before you patched, treat the host as compromised, image it, rotate every secret the worker could read, and rebuild from a patched image.
